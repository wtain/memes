Batch jobs are the highest-risk untested code: they are destructive (`rebuild_duplicates` drops the table), not idempotent in some cases, and run against production data.

### CI trigger gap

`backend-tests.yml` only watches `Backend/**`, `Storage/**`, `requirements.txt`. A breaking change in `repository/`, `rules/`, `ai/`, or any other shared root module will not trigger tests. This is a hidden regression risk.

### Duplication and dead code

- `image_repository.py:259` — `get_duplicates_precomputed` is labeled `# copy of the above` and appears unused. The active method is `get_duplicates_clustered`.
- Two rules engines (`rules/engine.py` and `rules/concept_tagger.py`) coexist with no transition plan documented in code.
- `batch/experimental/` — 14 scripts with no documented status.
- `models.py:102–128` — raw SQL in a multi-line string between class definitions. Not a docstring, not a migration — maintenance hazard.
- Commented-out `get_duplicates` call in `images.py:131`, stale commented-out uvicorn commands in `main.py:45–48`.

### Production `print()` statements

- `images.py:158` — `print(f"{filename}: {mime_type}")` with a `# todo: logging` comment
- `images.py:165` — `print(repr(cd))` with a debug comment

### Architecture description vs. reality

CLAUDE.md says "Strict two-layer: Router → Repository." A service layer (`Backend/app/services/`) exists and is actively used. The documented pattern is wrong.

### `image_store.py` crashes on import if `BASE_PATH` is unset

```python
images_dir = os.getenv('BASE_PATH')
IMAGES_DIR = Path(images_dir)  # TypeError if None
```

This makes the entire backend unimportable without a valid env file, which breaks cold-start debugging and any test that imports it without setting the env var.

## 3. Operational Excellence

### Logging

- No structured logging anywhere in the backend. `print()` is the logging mechanism.
- No log levels, no correlation IDs, no request tracing.
- If deployed to cloud (CloudWatch, GCP Logging, Datadog), `print()` goes to stdout — workable but gives no queryability or severity filtering.

### Health check is cosmetic

```python
@app.get("/health")
async def health_check():
    return {"status": "healthy"}
```

Returns healthy even if the DB is down. Any load balancer or Kubernetes liveness probe relying on this will be misled.

### Metrics

- `SimpleMetricsListener` exists for batch jobs but has no persistence and no export to any metrics backend.
- No request-level metrics (latency, error rates) on the backend API.

### Backup / DR

- `Storage/backups/` directory exists — no documented procedure for what is backed up, when, and how to restore.
- Image files live on the local filesystem. If the machine dies, images are gone. No object storage strategy.
- Three-environment design (metal/general/IT) means three separate DBs — backup complexity is 3×.

### State transfer (local → cloud)

- Images are at a local Windows path (`c:\Users\ramiz\OneDrive\...`) baked into `.env.metal`. Migrating to cloud requires replacing all `BASE_PATH` references with object storage and rewriting `image_store.py` and every batch job that reads from `BASE_PATH`.
- No abstraction layer between "local filesystem" and "blob storage" — `Path` is used directly everywhere.

### Environments not containerized as a whole

- `Storage/docker-compose.yaml` runs only the DB.
- No compose file that runs backend + DB + frontend together.
- The Readme's "One-Command Setup (Docker): `docker-compose up -d`" does not work today.

## 4. Overall Structure

### What works well

- Root-level Python packages (`repository/`, `ai/`, `rules/`, etc.) shared between Backend and batch is the right pattern.
- Shared JSON schemas (`shared/schemas/`) driving TypeScript and Kotlin code generation is solid contract management.
- Three-environment isolation via env files is clean.

### What is hard to navigate

Root level mixes: Python source packages, application directories (Backend, Frontend, AndroidClient), infrastructure (Storage), tooling (environments), and multiple doc files. No README map of what depends on what. A new developer sees 20+ top-level entries with no dependency graph.

**Implicit Python dependencies:** Backend imports `repository/`, `ai/`, `rules/`, `embeddingutils/`, `graph/`, `metrics/` via `sys.path` manipulation in `conftest.py`. There is no `pyproject.toml` or explicit package structure — you cannot `pip install` the shared modules. This works in Docker only because the Dockerfile copies the right directories manually.

**Two venvs:** `.venv` (Python 3.13) and `.venv311` (Python 3.11). The project targets 3.11. The 3.13 venv has no documented purpose and adds confusion.

**`batch/experimental/`:** 14 scripts, a `yolov8n.pt` model file, no README, no indication of which are still useful. This directory will grow forever without a clear archival policy.

## 5. Security

### Current issues (pre-public deployment)

| # | Issue | Location | Severity |
|---|---|---|---|
| 1 | Upload endpoint: MIME type taken from client header | `uploads.py:62` | High |
| 2 | `None` in CORS allow_origins if env vars unset | `main.py:28–31` | Medium |
| 3 | No authentication on any endpoint | All `/api/*` | Low (private use only; see note) |

> **Keystore (`AndroidClient/memebrowser-release.jks`):** verified not tracked in git and not present in git history. No action needed.

### Detail

**Upload MIME spoofing** — `content_type = file.content_type or ""` trusts the client-supplied Content-Type header. An attacker can send a PHP script with `Content-Type: image/jpeg`. Magic byte validation (check actual file header bytes) is required.

**`None` in CORS origins** — if `FRONTEND_ORIGIN` or `ALTERNATIVE_FRONTEND_ORIGIN` are unset, `None` enters the `allow_origins` list. Starlette's behavior with `None` in this list is undefined/implementation-dependent.

**No authentication** — all endpoints are open. Acceptable while the app is private/internal. When deploying publicly, a read-only mode (search + browse, no uploads/mutations) may avoid the need for auth initially. Full auth design should precede any write-endpoint exposure.

### Missing for public cloud

- No rate limiting (upload endpoint accepts 50 × 20 MB = 1 GB per request, unlimited frequency)
- No HTTPS/TLS termination mentioned in deployment docs
- No secrets management — credentials in plain `.env` files
- No content moderation on uploaded images
- DB credentials are `ocr:ocr` in default env files — needs rotation for prod
- No CSRF protection on mutation endpoints (PUT)
- `/health` endpoint does not verify DB — misleads orchestration tooling

## 6. Database Schema Documentation

### Current state

The canonical schema definition lives in `Storage/models.py` (SQLAlchemy ORM models). The only other schema reference is a high-level prose description in `ARCHITECTURE.md` — but it is inaccurate in several places:

| Discrepancy | `ARCHITECTURE.md` | Actual (`models.py`) |
|---|---|---|
| Embedding dimension | 1536 | 512 (`EMBEDDING_DIM = 512`) |
| `image_embeddings` table name | `image_embeddings` | `embeddings` |
| `tags` table structure | Described as a separate tag catalogue + junction table | Single `tags` table with `image_id`, `key`, `value`, `source` — no separate catalogue |
| `concepts` table | `embedding (Vector 1536)` | `Vector(512)`, with a `# Deprecate` comment on the field |
| `duplicate_clusters` table | Described as storing "groups of similar images" | Actual tables are `tmp_duplicates` (pairwise) and `tmp_clusters` (cluster membership) — both named `tmp_*` suggesting they are intermediate, not permanent |

### What is missing

- No ER diagram or visual schema.
- No table-level descriptions explaining the purpose and lifecycle of each table (e.g., when `tmp_duplicates` is safe to drop, what `image_processing_status` tracks, why `ImageExtras` is separate from `Image`).
- No column-level notes on nullable fields, enums, or invariants (e.g., `ImageProcessingStatus.status` can be `processing | done | failed` — this is only in a code comment, not in any schema doc).
- No index documentation — indexes are defined in migrations and in `__table_args__` but never surfaced in a human-readable form.
- Alembic migration history is not documented (no changelog of what each migration changed).
- The `Concept.embedding` field has a `# Deprecate` comment with no replacement path documented.

### Risk

A developer modifying the schema has no quick reference to understand table relationships, expected cardinalities, or which tables are temporary vs. permanent. The `tmp_*` naming convention is informal and not documented as a pattern.

## 7. Type Contract Integrity

### What works

Shared JSON schemas (`shared/schemas/`) drive TypeScript type generation (`generate-types.sh`) and Kotlin DTO generation (`generate_dtos.py`). This is a sound contract management approach.

### What is fragile

- Type generation is manual — no CI step enforces that generated types are current with schemas. A schema change that is not regenerated silently drifts.
- `backend_api.md` is manually maintained and described as "authoritative," but there is no automated API contract validation (no Schemathesis, no Dredd).
- Several Frontend types (`src/types/facet.ts`, `src/types/statistics.ts`, `src/types/trends.ts`) appear hand-written rather than generated from schemas, creating two parallel type sources.

## Summary

**Biggest single security risk:** Upload endpoint accepts any MIME type the client declares — no magic byte validation.

**Biggest documentation gap:** The database schema docs in `ARCHITECTURE.md` are inaccurate in multiple places, and there is no ER diagram or lifecycle description for any table.

**Biggest structural risk:** CI does not watch shared Python modules (`repository/`, `rules/`, `ai/`), so regressions in those modules go undetected until manual testing.

**Biggest operational gap:** `docker-compose up -d` referenced in the Quick Start does not work — there is no root-level compose file.
