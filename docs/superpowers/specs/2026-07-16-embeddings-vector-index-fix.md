# Fix the ineffective btree index on `embeddings.embedding`

## Context

`Storage/models.py`'s `Embedding` model (the CLIP image-embedding table,
`EMBEDDING_DIM = 512`):

```python
class Embedding(Base):
    __tablename__ = "embeddings"
    id = Column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4, index=True)
    image_id = Column(UUID(as_uuid=True), ForeignKey("images.id", ondelete="CASCADE"), index=True)
    embedding = Column(Vector(EMBEDDING_DIM), index=True)
    created_at = Column(DateTime, server_default=func.now())
```

The bare `index=True` on the `embedding` column gives SQLAlchemy no operator
class or index method to work with, so it falls back to its default:
Postgres btree. This traces to a specific, real migration history, not a
hypothetical:

- `embeddings.embedding` (as a pgvector `VECTOR(512)` column) was added in
  `b4df248964cf_add_something.py` (2026-03-07) — repurposing what had
  previously been an OCR-style table (it dropped `text`/`confidence`
  columns in the same migration).
- `id`/`image_id` got real, useful btree indexes for point lookups and the
  `images` FK join in `b68b18f09246_add_indexes.py` (2026-02-25, actually
  predates the column add above but targets the same table) — those are
  fine and out of scope here.
- The `embedding` column's own index was added over a month later in
  `Storage/alembic/versions/18ec91d67615_embeddings_index.py`
  (2026-04-13), an **unedited autogenerated migration**:
  ```python
  op.create_index(op.f('ix_embeddings_embedding'), 'embeddings', ['embedding'], unique=False)
  ```
  No index method, no operator class — Alembic/SQLAlchemy silently emitted
  a plain btree `CREATE INDEX`, because that's the ORM's default and
  nothing in the model declaration told it otherwise.

### Why this is a real bug, not just theoretical

**1. It does nothing for the query it exists to support.** Postgres btree
indexes support equality and ordering comparisons on scalar types; they
provide no acceleration for pgvector's `<=>` (cosine distance) operator.
Reading `Backend/app/repositories/image_repository.py`, exactly one query
is the classic case this index should be helping:

```python
async def get_similar(self, image_id: str, embedding, limit: int = 10):
    ...
    .order_by(embed.embedding.cosine_distance(embedding))
    .limit(limit)
```

This is `ORDER BY embedding <=> :query_vector LIMIT k` — precisely what an
ANN (approximate nearest neighbor) index (`hnsw`/`ivfflat`) is built to
accelerate. Today, backing it with a btree index, Postgres cannot use the
index at all for this predicate and falls back to a full sequential scan
plus in-memory sort over every row in `embeddings` on every call to
`GET /api/images/{image_id}/similar`.

To be precise about the other `cosine_distance` call sites in the same
file, since an ANN index would **not** help all of them equally:

- `get_duplicates` also calls `.cosine_distance()`, but as a self-join
  distance *filter* between two aliased copies of the table
  (`embed1.embedding.cosine_distance(embed2.embedding) < threshold`),
  ordered by `created_at`, not by distance. This compares every row's
  vector against every other row's vector rather than searching for
  neighbors of one fixed query vector — the same O(n²) shape already
  flagged (and explicitly left unaddressed) in
  `docs/adr/adr-2026-07-10-tmp-duplicates-fk-index.md` for
  `tmp_duplicates`. An ANN index does not accelerate this query shape;
  fixing it is a separate, larger problem, out of scope here, same as
  that ADR's own scope cut.
- `get_duplicates_precomputed` and `get_duplicates_clustered` don't call
  `cosine_distance` against `Embedding` at request time at all — they read
  precomputed results from `TmpDuplicates`/`TmpImageClusters`, tables
  built offline by `batch/rebuild_duplicates.py` / `batch/clusterize.py`.
  Unaffected by this table's index either way.
- The raw all-pairs SQL embedded as a comment directly above `TmpDuplicates`
  in `Storage/models.py` (`ie1.embedding <=> ie2.embedding` under
  `JOIN image_embeddings ie2 ON true`) reads every row against every other
  row with no bound query vector — also not something an ANN index can
  speed up.

So the concrete, immediate win from fixing this index is the
`get_similar` query behind `GET /api/images/{image_id}/similar` — real,
user-facing, and currently unaccelerated. The rest of the file's
`cosine_distance` call sites either don't touch this table at request time
or have a query shape ANN indexes don't help with.

**2. Beyond query performance, the current index is dead weight on every
write.** A btree index over a 2048-byte vector column still has to be
maintained (and disk space paid for) on every `INSERT`/`UPDATE` to
`embeddings`, for an index Postgres can never actually use for the
`ORDER BY ... cosine_distance(...)` query it needs to serve — `build_image_embeddings.py`
pays this cost on every image processed for zero query benefit today.

**3. It only avoids crashing by luck of the dimension count.** Postgres
btree indexes cap indexed tuple size at roughly 2704 bytes (the
"1/3 of the 8KB page, minus overhead" btree version-4 limit). 512
floats × 4 bytes = 2048 bytes of raw vector data, plus ~16–24 bytes of
index-tuple/page overhead, lands at roughly 2064–2072 bytes — under the
cap, so `embeddings` has never actually crashed on this. The identical
`index=True` pattern was reused for the newer `ImageDescriptionEmbedding`
table (`TEXT_EMBEDDING_DIM = 1024`, added in
`2026_07_13_rename_ollama_description_to_image_descriptions.py`) and did
cross that threshold, throwing `index row size 4112 exceeds btree
version 4 maximum 2704` on every insert — a hard failure, since fixed
separately and out of scope for this spec. `embeddings` has the exact same
underlying defect; it has simply never been exercised past the byte
threshold that would make it crash instead of merely being useless.

### Why this is harder than the sibling table's fix

`ImageDescriptionEmbedding` was empty when its index issue was hit — any
fix there was a same-day schema edit against zero rows. `embeddings` is
different: it's a live, populated table in all three real environments
(`metal`, `general`, `it` — each its own Postgres instance per
`environments/Environments.md`, ports 5432/5434/5436 respectively).
`general` alone is documented at 22,402 images as of
`docs/adr/adr-2026-07-10-tmp-duplicates-fk-index.md` (and ~21,954–22,000 in
the more recent `docs/superpowers/specs/2026-07-15-image-description-failure-tracking-and-context-size.md`),
essentially one row per image in `embeddings` too (`build_image_embeddings`
runs one embedding per registered image). `metal` and `it` row counts are
not established in any doc read for this spec — see the Rollout section's
pre-flight checklist.

This repo already has a directly relevant incident write-up for "index
build against a populated table went badly":
`docs/adr/adr-2026-07-10-tmp-duplicates-fk-index.md` covers a 100+ minute
stalled index build at the default `maintenance_work_mem` (64MB) on a
489M-row table, a 7+ hour cascade-delete stall from the *missing* index
before that, and a full recovery playbook (`pg_stat_activity`,
`pg_locks`, `pg_stat_progress_create_index`, bumping
`maintenance_work_mem` to 2GB). `embeddings` is four orders of magnitude
smaller (tens of thousands of rows, not hundreds of millions), so a
multi-hour stall is not expected — but the playbook's monitoring
commands and the general lesson ("confirm with `pg_stat_progress_create_index`,
don't guess") still apply, and are cheap to reuse regardless of scale.

## Decision: replace the btree index with a single HNSW index using `vector_cosine_ops`

```sql
CREATE INDEX CONCURRENTLY ix_embeddings_embedding_hnsw_cosine
    ON embeddings USING hnsw (embedding vector_cosine_ops);

DROP INDEX CONCURRENTLY ix_embeddings_embedding;
```

The operator class matters as much as the index method: pgvector requires
the index to be built with the operator class matching the distance
operator actually used in queries. `get_similar` calls `.cosine_distance()`,
which compiles to the `<=>` operator — that requires `vector_cosine_ops`.
Building with the default (`vector_l2_ops`, for `<->`/Euclidean distance,
which nothing in this codebase's `Embedding` queries uses — confirmed via
a repo-wide search for `cosine_distance`/`l2_distance`/`max_inner_product`
against `Embedding`) would compile, "exist" in `pg_indexes`, and still
never be picked by the planner for the actual query — a second, subtler
way to end up with a silently-useless index. `vector_cosine_ops` is the
correct and only choice needed here.

### HNSW vs. IVFFlat — reasoning, not just a pick

Both are real, viable pgvector 0.8.2 ANN index types (confirmed installed
via `psql -c "SELECT extversion FROM pg_extension WHERE extname='vector';"`
per the diagnosed-bug write-up this spec is based on). The two differ in
a way that's actually relevant to this specific table, not just
generically:

- **IVFFlat needs a representative sample of real data already present**
  to build good cluster centroids (it's a k-means-style partitioning of
  the existing rows at `CREATE INDEX` time). `embeddings` — unlike the
  empty `ImageDescriptionEmbedding` table, which had no choice but to pick
  a method that tolerates being built empty — genuinely has this
  precondition met: tens of thousands of real CLIP embeddings already
  populated. So "IVFFlat needs real data" is not actually a blocker here;
  it's the one condition under which IVFFlat is a fair fight.
- **IVFFlat's centroids go stale as new data is inserted without a
  rebuild.** `embeddings` is not a static, one-time-populated table — new
  rows are appended continuously by `build_image_embeddings.py` every time
  new images are registered (the batch pipeline's second stage per
  `CLAUDE.md`). If new images' embeddings land in a distribution the
  original centroids don't represent well, IVFFlat's recall degrades over
  time until someone reruns `REINDEX`/rebuilds the index — an ongoing,
  easy-to-forget maintenance burden this repo has already been bitten by
  once for a different reason (`tmp_duplicates`'s non-idempotent rebuild
  requirement, and the FK-index gap that went unnoticed until it caused a
  multi-hour stall).
- **HNSW's graph is built incrementally and updates naturally with each
  insert** — no separate "rebuild to stay fresh" step as the table grows.
  It costs more per-insert than IVFFlat (graph-node insertion vs. simple
  cluster assignment) and is somewhat more memory-hungry to build, but
  inserts here happen exclusively through an offline batch job
  (`build_image_embeddings.py`), never on a request's hot path — so a
  heavier per-row insert cost is an acceptable trade against a
  interactive-facing query's neighbor-search that pgvector's own
  documentation and general community consensus consistently report HNSW
  answering faster and more accurately than IVFFlat at equivalent recall.
- **Consistency with the sibling table.** The already-fixed
  `ImageDescriptionEmbedding` table uses HNSW (chosen there specifically
  *because* it tolerated being empty). Using HNSW here too means this
  codebase has one ANN index method for "vector column that backs a
  live nearest-neighbor query," not two, which is one less thing to
  remember when either table's index needs touching again later.

**Recommendation: HNSW**, with pgvector's default build parameters
(`m = 16`, `ef_construction = 64`) — reasonable for a table in the tens of
thousands of rows, not the scale where those defaults need tuning. No
special `hnsw.ef_search` tuning up front either; revisit only if
post-rollout verification (below) shows recall or latency issues in
practice.

## Migration mechanics: `CREATE INDEX CONCURRENTLY` outside Alembic's transaction

Alembic wraps each migration's `upgrade()` in a single transaction by
default, and Postgres flatly rejects `CREATE INDEX CONCURRENTLY` /
`DROP INDEX CONCURRENTLY` inside a transaction block
(`ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`).
Without `CONCURRENTLY`, a plain `CREATE INDEX` takes a `SHARE` lock that
blocks all writes to `embeddings` for the build's full duration — on a
live environment serving real traffic on `get_similar`/`get_duplicates`
and being written to by whatever batch job is running, that's the
behavior we specifically want to avoid, even at this table's modest size.

Alembic has a documented pattern for exactly this: `autocommit_block()`,
which ends the migration's ambient transaction, runs the enclosed
statements each in their own autocommitted connection, then resumes
Alembic's normal transactional mode after the `with` block:

```python
def upgrade() -> None:
    with op.get_context().autocommit_block():
        op.execute(
            "CREATE INDEX CONCURRENTLY ix_embeddings_embedding_hnsw_cosine "
            "ON embeddings USING hnsw (embedding vector_cosine_ops)"
        )
        op.execute("DROP INDEX CONCURRENTLY ix_embeddings_embedding")


def downgrade() -> None:
    with op.get_context().autocommit_block():
        op.execute(
            "CREATE INDEX CONCURRENTLY ix_embeddings_embedding "
            "ON embeddings (embedding)"
        )
        op.execute("DROP INDEX CONCURRENTLY ix_embeddings_embedding_hnsw_cosine")
```

`CONCURRENTLY` holds only a `SHARE UPDATE EXCLUSIVE` lock — it blocks
other DDL and `VACUUM` on `embeddings`, but not ordinary reads or writes,
which is the whole point of using it over a plain `CREATE INDEX` here.

Two operational notes carried over directly from the `tmp_duplicates`
precedent (`docs/adr/adr-2026-07-10-tmp-duplicates-fk-index.md`):

- **Bump `maintenance_work_mem` before building, even though this table is
  small.** The prior incident's default (64MB) caused a 100+ minute stall
  with no visible progress on a 489M-row table; `embeddings` at
  tens-of-thousands of rows is very unlikely to need it, but setting
  `SET maintenance_work_mem = '256MB';` session-scoped immediately before
  the `CREATE INDEX CONCURRENTLY` is cheap insurance with no downside.
- **Monitor with `pg_stat_progress_create_index`, don't guess it's done:**
  ```sql
  SELECT pid, phase, blocks_total, blocks_done, tuples_total, tuples_done
  FROM pg_stat_progress_create_index;
  ```
  A concurrent build adds an extra validation-scan phase beyond a regular
  build (it has to re-scan for rows written during the initial scan) —
  expect `phase` to move through `building index: scanning table` →
  `building index: loading tuples in tree` → a validation phase before
  the row disappears. Cross-check `pg_indexes` afterward to confirm the
  new index exists and is not marked `INVALID` (a `CONCURRENTLY` build
  that fails partway leaves behind an unusable `INVALID` index rather than
  cleanly rolling back — `DROP INDEX` it and retry if that happens).

## Verification plan

Existence in `pg_indexes` is not sufficient proof the fix worked — the
planner has to actually choose the new index for the real query shape.
Per environment, before and after running the migration:

```sql
EXPLAIN ANALYZE
SELECT e.image_id, e.embedding <=> '[... a real 512-dim vector ...]'::vector AS distance
FROM embeddings e
ORDER BY e.embedding <=> '[... same vector ...]'::vector
LIMIT 10;
```

- **Before:** expect `Seq Scan on embeddings` followed by a `Sort` node —
  confirming the current btree index is indeed unused for this query
  (the predicted, but until now unverified, state).
  Non-negotiable to run before-and-after here, not to accept the (later,
  post-implementation) fix on faith the same way the bug's original
  diagnosis was accepted on faith.
- **After:** expect an `Index Scan using ix_embeddings_embedding_hnsw_cosine`
  (or `Index Scan` in HNSW's typical form — no separate `Sort` node needed,
  since the index returns rows in approximate distance order already) in
  the plan, and a materially lower `actual time`.
- Additionally hit the real endpoint (`GET /api/images/{image_id}/similar`
  against a running `metal`/`general`/`it` backend) before and after and
  confirm both response shape and the returned neighbor set are sane —
  HNSW is an *approximate* nearest-neighbor method, so a handful of
  borderline-distance results changing rank order slightly versus the old
  exact sequential scan is expected and acceptable; the same well-known
  near-duplicates for a test image should still come back.
- Confirm the old index is actually gone: `SELECT indexname, indexdef FROM
  pg_indexes WHERE tablename = 'embeddings';` should show only
  `ix_embeddings_id`, `ix_embeddings_image_id` (both legitimate, untouched
  by this spec), and the new `ix_embeddings_embedding_hnsw_cosine` — not
  the old `ix_embeddings_embedding` btree.

## Rollout across `metal`, `general`, `it`

Each environment is a fully separate Postgres instance
(`environments/Environments.md`: `metal` port 5432, `general` port 5434,
`it` port 5436) — this migration must be applied independently to each,
there is no shared database.

**Pre-flight checklist (do this before scheduling any environment's
run):**

1. `SELECT count(*) FROM embeddings;` against each of the three databases.
   `general` is already known to be roughly 22,000 (per the ADR and the
   more recent image-description spec, both citing ~22k images, and
   `embeddings` tracks one row per registered image). `metal` and `it`'s
   counts are not established in this repo's existing docs — check them
   directly rather than assuming they're smaller; if either turns out to
   be comparably large, treat it with the same care as `general` below.
2. Confirm each environment's Postgres/pgvector version supports HNSW
   (pgvector ≥ 0.5.0; already confirmed 0.8.2 in this dev environment,
   but that check was against one instance — verify each of the three
   separately since they're independent installs).

**Rollout order:** apply to `metal` and `it` first if the pre-flight
check confirms they're meaningfully smaller than `general` — lower risk
to validate the migration's mechanics (autocommit block behaves as
expected, index gets built and picked up by the planner) against a
faster, cheaper run before touching the largest dataset. Apply to
`general` last, with the `maintenance_work_mem` bump and
`pg_stat_progress_create_index` monitoring from the previous section
actively watched during the build, not just queued and left unattended —
consistent with this repo's existing precedent that the safe way to run
a live index build is to watch it, not assume it'll finish.

Since Alembic migrations apply in a fixed order per environment
(`alembic upgrade head`, from `Storage/`, per `CLAUDE.md`), and each
environment has its own migration history/connection via
`environments/.env.<environment>`, this is naturally three separate
`alembic upgrade head` runs — no cross-environment coordination needed
beyond doing them in the order above and watching each one.

## Out of scope

- Fixing `get_duplicates`'s O(n²) self-join distance filter, or the
  identical-shaped all-pairs query behind `tmp_duplicates` — both
  explicitly left unaddressed by the precedent ADR this spec builds on,
  and neither is something an ANN index on `embeddings.embedding` fixes.
- Any change to `ImageDescriptionEmbedding`/`image_description_embeddings`
  — that table's index situation is a separate, already-handled piece of
  work.
- Tuning `hnsw.ef_search`, `m`, or `ef_construction` beyond pgvector's
  defaults — revisit only if the verification step above shows a real
  recall or latency problem at actual production scale.
