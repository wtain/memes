# Interfaces: the single contract of the dev/prod sync epic

Status: draft (reconciled 2026-11-12; decisions 26 (dry-run report) and 27 (no removals for now) applied 2026-11-12; the project designs P2 to P7 reference this file instead of redefining these names)
Originates from: docs/superpowers/specs/2026-11-12-environment-data-sync/tracker.md

This file is authoritative for every name, file, field, age, flag, role, port and gate verb that two or more documents share. The designs
(P2 to P7) own the behaviour; this file owns the spelling. If a design and this file disagree, this file wins and the design is wrong.
The built P1 registry (`sync/`, `docs/sync-registry.md`) is authoritative for the table lists (46 tables: 22 D, 6 P, 18 X). S5 stays a closed
analysis; where this file differs from S5 it says so (section h).

Vocabulary: `<env>` is `metal`, `general` or `it`. "Dev" is the workstation, "prod" the VPS stack of that environment. "Logical role"
names (`backend_app`, `sync_writer`, `sync_reader`, `read_only`, `owner`) are the registry/S5 names; the concrete Postgres names are in (d).

## a. State directory `Storage/sync-state/<env>/` (git-ignored, one per environment)

Resolved by `sync/config.py` (tracked setting `sync.state_dir`, default `Storage/sync-state/<env>`). Files are written atomically (temp file, `fsync`,
`os.replace`). Run id format: `YYYYMMDDTHHMMSSZ-<8 hex>`; one id per `sync.run`, or generated by a tool run on its own. A run folder
created by a dry run holds an empty marker file `dry`; no consumer ever accepts a file from a folder with that marker. The marker folder still holds `report.json` and `report.md` (section k),
which are for the owner and never an input.

## b. Settings and secrets

**Secrets** (gitignored, restricted permissions, never in agent sessions, decisions 18 and 21): `environments/.env.<env>.sync`, credentials only:
`SYNC_WRITER_PASSWORD`, `SYNC_READER_PASSWORD`. Read with `dotenv_values` into a dict, never into `os.environ`; the loader refuses a file that git tracks and
warns when other Windows accounts can read it. Ambient `PROD_*` variables do not exist and are ignored with a warning naming them. ssh keys live in the user's
ssh config (agent), not in this file. Dev database access comes from `environments/.env.<env>` through `config.settings.load_env`: read-only tools use
`DATABASE_URL_READONLY`, `sync.pull` uses `DATABASE_URL` (it writes the class P mirror).

Directory contract: `images` is `BASE_PATH` (owner `memesync-<env>`, group `memesync-<env>`, directories 2755, files 0644, gate umask 022; the backend container user
`1000:<gid of memesync-<env>>` reads it as "other" through a `:ro` mount). `work` (batches, `record.tsv`, `counters.json`, `gate.lock`) and `retired` (`<date>/`; provisioned now, used only once removals are built, decision 27) are
mode 0700, owned by `memesync-<env>`, **on the same filesystem as `images`** (the gate `handshake` exits 3 otherwise). `staging` is the chroot root of `memeup-<env>`
(root-owned); its only writable directory is `staging/incoming` (owner `memeup-<env>`, group `memesync-<env>`, mode 2770). `bug-reports` is `BUG_REPORTS_PATH`, outside
`images` (owner 1000, group `memesync-<env>`, 2775, files 664). Gate program `/opt/memes/memesync-gate.py`, config `/etc/memes/gate.conf` (root-owned, one section per
environment). The gate never receives the docker socket: container and disk facts (verbs `containment`, `disk`) come from files a root-run P5d timer writes
under `/var/lib/memes/<env>/` (`containment.json`, `disk.json`) which the gate only prints.

Per-environment passwords and keys are separate: a credential of one environment never works for another.

## e. Identity handshake (`sync/connect.py: handshake()`)

Run by every `sync.*` command before its first read of dev data or write of prod; any failure is exit 2 with a one-line reason (no row content). Which tool runs which
steps is in the last column of the table (P = promote, F = files, L = pull, V = verify, R = run, D = doctor; R and D run all the steps their children need).

| # | Check | Expected from | Tools |
|---|---|---|---|
| H1 | Dev side: `APP_ENV` equals `--env`; the dev URL kind is right for the tool (read-only URL for P, F, V; write-capable `DATABASE_URL` for L, the read-only URL refused there); dev `current_database()` equals `sync.dev.database`; dev has no `memes.environment` setting | tracked | all |
| H2 | Tunnel up from `sync.prod.ssh_alias`; prod `current_database()` equals `sync.prod.database` | tracked | all that use the database |
| H3 | (P6 V: the writer in a read-only session, and the reader when the tool opened one for the class P counts) Prod `current_user` equals `sync.prod.writer_role` or `reader_role` as the tool needs; not superuser/owner/backend (`pg_has_role`); no `rolcreaterole`, `createdb`, `replication`, `bypassrls`; `has_table_privilege` INSERT/UPDATE/DELETE/TRUNCATE false on every class P and X table and true on the class D tables it writes (writer only); `has_column_privilege` SELECT only on `meme_text_ratings (image_id, query_hash, updated_at)` for the writer (section h) | registry | P, L, V (F only once the deferred retire row check is built) |
| H4 | `current_setting('memes.environment')` equals `--env` | `--env` | all that use the database |
| H5 | `GET <sync.prod.api_url>/api/diagnostics/capabilities`: `environment` equals `--env`, `stage = prod` (nothing else is compared: section f) | `--env` | P, L, V, R, D |
| H6 | Gate: `handshake` verb prints `environment` equal to `--env` (fixed by the key), gate version, device ids | `--env` | F, L (bug reports), V (S4), R |
| H7 | Not the same server: dev and prod differ in at least one of `(inet_server_addr, port)`, `pg_postmaster_start_time()`, database oid, `pg_control_system().system_identifier` | both | P, V, R |
| H8 | Id overlap (not liftable): if prod has images, at least half of prod's image ids exist in dev's `images`; a pairing with another environment has overlap 0 | both | P, V, R |
| H9 | `current_setting('memes.state')` is `serving` (normal) or `seeding` (`--first-seed`) | mode | P, R |
| H10 | Release: `alembic_version` equal on both sides and `current_setting('memes.revision')` equals the dev working tree's git SHA (a mismatch is a precondition failure; this replaces `--ack-revision`); capabilities are not consulted | both | P, V, R |

Database settings (set on the prod database by the roles: `memes.environment` and `memes.state` by the owner role in `provision.sh`, P5d; `memes.revision` at every release,
release runbook step 3): `memes.environment` = `<env>`; `memes.state` = `seeding` while the database is being first-seeded without HNSW/GIN indexes, `serving` once the owner
rebuilt the indexes and flipped it (there is no separate marker file and no other seeding flag); `memes.revision` = git SHA of the deployed image.
Banner printed on every run and repeated at the confirmation: `dev <env> (<dev db> @ localhost, read-only) -> prod <prod db> as <writer role> via ssh alias <ssh_alias>`.
Typed confirmation (when `--apply` without `--yes`; owner decision B, 2026-11-14): the question names what the command writes. Tools that write PROD (`sync.promote`, `sync.files promote`) ask `<env> <prod database>`: `sync.promote` reads the name back from the server
(`current_database()`), `sync.files promote` uses `sync.prod.database` (it opens no database session). Stand-alone `sync.pull` asks `<env> <dev database>` (it overwrites dev's mirror of the class P tables; prod is only read). `sync.run --apply` asks ONCE `<env> <prod database read back from the server>` (read in its step 0) and passes `--yes` to its steps.

## f. Capabilities payload (P5a-T4; `GET /api/diagnostics/capabilities`, public)

```json
{ "stage": "prod", "environment": "general",
  "features": { "memeFromText": false, "concepts": true, "trends": false, "comics": false,
                "ratings": false, "statistics": false, "uploads": false, "history": false, "admin": false } }
```

through the database. P4 reads `features.ratings` for `ratings_mode` consistency. Web and Android effective visibility = build flag AND capability.

## g. The gate: `deploy/prod/memesync-gate.py`

One Python 3 standard-library file (Python 3.9 or newer on the VPS, no tar/find/sha256sum calls), **owned and written by P3-T3**, installed by P5d-T5. It is the forced
command of the verb key: `restrict,command="/usr/bin/python3 /opt/memes/memesync-gate.py <env>"` in `~memesync-<env>/.ssh/authorized_keys`; the environment is the first
argument and the client cannot choose it; the verb is `SSH_ORIGINAL_COMMAND`. Per account `memesync-<env>`: the **verb key** (above, no sftp, no shell), and a **tunnel key**
`restrict,port-forwarding,permitopen="127.0.0.1:<pg_port>",command="/bin/false"` (answers P3 review question 2). Account `memeup-<env>`: sshd `Match User`, `ChrootDirectory`
`/srv/memes/<env>/staging`, `ForceCommand internal-sftp -u 007`, no forwarding, no tty. There is no `memesync-gate.sh` and no `memesync` shared user.

Locking: verbs marked L run under `flock` of `work/gate.lock` of the environment. Names arrive NUL-separated on stdin, are parsed by the Python gate only, and every
filesystem call uses a validated final name relative to a directory fd. Caps live in `/etc/memes/gate.conf` and are lifted only by editing that file on the VPS (never a
client flag): `max_member_mb` 200, `max_members` 5000, `max_batch_mb` 600, free-space floor 10 %, replace-on-commit per day `max(200, 5 %)`. The `retire`/`restore` caps (per call `max(50, 2 %)`, per day
`max(100, 5 %)`) belong to the deferred verbs and are not built now (decision 27).

| Verb | Lock | Owner design | Does |
|---|---|---|---|
| `handshake` | | P3 | environment, gate version, device ids, free space of the files volume and the Postgres volume, uid/mode probe, the active caps; exit 3 on device mismatch, free space below floor, unreadable probe |
| `list` | | P3 | one record per entry directly in `images`: `type TAB size TAB sha256-from-record TAB nlink TAB uid TAB mode TAB name NUL`; `type` is `f` for regular files, anything else (link, dir, fifo, socket, device, hidden) is listed with its type so P6 F4 sees it; P3's diff uses only `f` with `nlink 1` and reports the rest as anomalies; names with tab/newline/non-UTF-8 bytes are `invalid` entries |
| `hash [--names]` | L | P3 | recomputes sha256 of the named files (or all) and rewrites `work/record.tsv` (`--deep`, rebuild after a restore) |
| `receive <id>` | L | P3 | copies `staging/incoming/<id>.tar` into `work/`, strict extraction (regular files only, `O_EXCL|O_NOFOLLOW`, name regex, caps) into a new `work/<id>/`, writes the validated list |
| `verify <id>` | | P3 | sha256 and size of every extracted file against the sums on stdin; any difference deletes the batch, exit 1 |
| `commit <id>` | L | P3 | `os.replace` each validated name into `images`, appends the record, counts replacements against the daily cap, removes the batch |
| `sweep` | L | P3 | deletes `work/*` batches and `staging/incoming/*` older than 6 hours (also run by a P5d systemd timer) |
| `pull-list` | | P4 | flat regular non-hidden files in `bug-reports` older than 60 s: name, size, sha256; anomalies reported |
| `pull-tar` | | P4 | the named bug reports as a tar on stdout (names validated against `^[0-9TZ_-]+_[0-9a-f-]{36}\.[a-z0-9]{1,8}$`) |
| `delete-verified` | L | P4 | deletes the named bug reports after re-checking each sha256 against the one sent |
| `fetch-backup` | | P5 | read-only: newest class P dump of this environment and its metadata (size, mtime, `pg_restore --list` result recorded by `backup.sh`). P6 sends only `fetch-backup --meta` and reads `meta.pg_restore_list == "ok"` |
| `disk` | | P5 (needed by P6 A3) | prints `/var/lib/memes/<env>/disk.json`: free space per mount of this environment (database volume, images, staging, backups, container logs). The shape P6 reads: `{"mounts": {"<mount>": {"free_pct": n}}}` (or `free_bytes` and `total_bytes`), also the bare mount map; any other shape makes A3 skipped (`facts_unusable`) |
| `containment` | | P5 (needed by P6 S8) | prints `/var/lib/memes/<env>/containment.json`: the backend container's mount modes, read-only root, `cap_drop`, `no-new-privileges`, user, published ports. The shape P6 reads: `{read_only_root: bool, cap_drop: [..], no_new_privileges: bool, user: str, base_path_read_only: bool, published_ports: [str]}` |

**Deferred verbs (decision 27, not built, no caps built):** `retire` (L; moves named files to `retired/<date>/`, numeric suffix, never over an entry, drops them from the record, volume caps), `restore <date>` (L; moves named
files back if the name is absent, never overwrites) and `purge` (L; deletes `retired/<YYYY-MM-DD>/` directories older than 14 days). Their design text is in P3's deferred section; the gate file is built without them and they are added under
the same rules (flock, name validation, no shell) when removals are built.

P3 delivers the file with its verbs; P4 verbs (T6 of P4) and P5 verbs (`fetch-backup` P5d-T7, `disk` and `containment` P5d-T5/T7 together with the timer) are added to the same
file under the same rules (flock, name validation, no shell).

| Logical role | Concrete name | Grants |
|---|---|---|
| owner | `memes_<env>_owner` | owns database and objects; migrations and index DDL; connects over the socket only; never used by a service |
| `backend_app` | `memes_<env>_app` | `USAGE` on schema; `SELECT` on every class D table; `SELECT, INSERT, UPDATE, DELETE` on exactly the six class P tables; `USAGE, SELECT` on the `meme_impressions` sequence; nothing on class X or `alembic_version` |
| `sync_writer` | `memes_<env>_sync_w` | `SELECT, INSERT, UPDATE, DELETE` on the 22 class D tables; `USAGE, SELECT, UPDATE` on sequences of integer-id D tables; `MAINTAIN` on D tables (`REINDEX`, `VACUUM`; PG17+); `SELECT` on `alembic_version`; **no `TEMP`** (P2 uses `execute_values`, no staging table); **the single exception to S5's rule "sync_writer has no privilege on any class P table": column-level `SELECT (image_id, query_hash, updated_at)` on `meme_text_ratings`** (made for the ratings guard of the retire, which is deferred, decision 27: the grant stays in the generated roles and the tests unchanged so that building removals later needs no grant change; unused today; no message text, no write); no write on any class P or X table |
| `sync_reader` | `memes_<env>_sync_r` | `SELECT` on the six class P tables; `SELECT` on `alembic_version`; `SELECT (id)` on `images` (P4 rating rule); no write anywhere, no class D table |
| `read_only` | `memes_<env>_ro` | `SELECT` on everything except `search_history`, `search_history_tags`, `meme_text_ratings`; never given to agents |

Database level: `REVOKE ALL ON DATABASE ... FROM PUBLIC` (removes `CONNECT` and `TEMP`), per-role `CONNECT`; `REVOKE CREATE ON SCHEMA public FROM PUBLIC`; no default privileges for any
role except the owner's own. Connection limits: app 24, sync_w 3, sync_r 3, ro 2, owner 3. Verify (P6) opens the class D digests through `sync_writer` with
`default_transaction_read_only`. The deferred `files retire` row check would also use `sync_writer` (read-only session): `sync_reader` has no `SELECT` on `images.filename`.
The database markers (`memes.environment`, `memes.state`, `memes.revision`) are set by the owner role: since PostgreSQL 15 that needs `SET` on those parameters, which `roles.<env>.sql` grants to the owner (and to no other role; P5d-T2, verified on PG18). The image is `pgvector/pgvector:pg18-trixie`, not `postgres:18` (no pgvector there). The P5 role test asserts exactly: the writer's privilege on `meme_text_ratings` is column `SELECT` on those three columns and nothing else, and `ON DELETE CASCADE`
from `images` into `meme_text_ratings` works without a `DELETE` grant (P5d-T2 verifies on PG18).

## i. Commands, flags, exit codes

Common to every command: `--env {metal,general,it}` (required), dry run by default **with a report (section k)**, exit codes below. Flags are defined once here; a tool lists only the subset it accepts.

| Command | Purpose | Flags it accepts (beyond `--env`) |
|---|---|---|
| `python -m sync.run` (P7) | driver: handshake, pull, files, data, verify (removals deferred, decision 27) | `--apply`, `--yes`, `--first-seed`, `--plan-hash`, `--stop-after STEP` (`handshake`, `pull`, `files`, `data`, `verify`), `--run-id`, `--top N`, `--json`, and every lifting flag below, forwarded to the step that owns it (`--allow-mass-change`, `--allow-model-change`, `--ignore-running-batches` to the data step; `--allow-empty-source`, `--allow-growth` to the pull; `--allow-shrink TABLE` by the table's class, D to the data step and P to the pull; `--skip-files` is the pull's bug-report skip only, the files step still runs) |
| `python -m sync.promote` (P2) | rows to prod (additions and overwrites only) | `--apply`, `--yes`, `--plan-hash`, `--first-seed`, `--verify-only`, `--only TABLE[,..]`, `--limit-images N`, `--batch-size N`, `--max-report-age` (default 2 h), `--top N`, `--run-id`, `--json`, lifting flags: `--allow-mass-change N`, `--allow-shrink TABLE` (class D, repeatable), `--allow-model-change`, `--ignore-running-batches` |
| `python -m sync.files promote` (P3) | files to prod (additions and replacements only; `retire` and `restore` are deferred, decision 27) | `--apply`, `--yes`, `--deep`, `--batch-mb N`, `--plan-hash`, `--top N`, `--run-id`, `--json` |
| `python -m sync.pull` (P4) | reader activity and bug reports to dev | `--apply`, `--skip-files`, `--plan-hash`, `--top N`, `--run-id`, `--json`, lifting flags: `--allow-empty-source`, `--allow-growth`, `--allow-shrink TABLE` (class P, repeatable) |
| `python -m sync.verify` (P6) | read-only drift and health report | `--json PATH` (writes the `verify.json` document, `-` for stdout), `--deep-files`, `--deep-net`, `--skip CHECK,..` (ids of the design, repeatable; listed as skipped with reason `skipped_by_flag`), `--fail-on warn`, `--top N`, `--run-id` |
| `python -m sync.doctor` (P2-T3) | handshake only, writes nothing | `--json` |
| `python -m sync.roles` (P5d-T1), `python -m sync.render` (P1, built) | generators | `--env` (roles); `--write`/`--check` (render) |

Shared flag definitions (one spelling, one meaning everywhere):

- `--apply`: perform the changes (otherwise a dry run that writes nothing on either side, and no file any consumer accepts; it does write the report of section k into a `dry` run folder).
- `--yes`: skip only the typed confirmation (section e: `<env> <prod database>` for `sync.run`, `sync.promote` and `sync.files promote`, `<env> <dev database>` for a stand-alone `sync.pull`). The owner is expected to have read the dry-run report before every apply (decision 26).
- `--plan-hash H` (the only name; `--plan-id` does not exist): with `--apply`, re-plan and refuse (exit 3) if the plan hash differs from the dry run's printed hash (section k). `sync.run` binds the combined plan hash; each tool its own.
- `--top N`: ids listed per category in `report.md` and in the stdout summary (default `sync.report.top_n`, 50). `report.json` always carries the complete lists.
- `--allow-mass-change N`: lift one guard; N must equal the planned count exactly. `--allow-shrink TABLE`: lift the regression guard for one table. `--allow-model-change` (promote only, no value): lift the model-change guard (the profile embedding model pair or taxonomy version of dev differs from prod's; the flag is not part of the plan hash). `--allow-growth`, `--allow-empty-source`: P4 guards. `--ignore-running-batches`: lift the dev running-batch precondition. None lifts the zero-image guard, the id-overlap check, any handshake step or mixed models among the promoted rows (a precondition, exit 2).
- `--first-seed`: allowed only while `memes.state` is `seeding`; resumable by running the same command again; refused when `serving`.
- `--verify-only`: only the verify phase against the newest `committed.json`.
- `--json PATH`: also write the machine report (`report.json`, counts and ids only) to PATH (`-` for stdout).
- `--run-id ID`: passed by `sync.run` to its children; a tool run alone generates one.
- Nonexistent, on purpose: `--i-have-pulled`, `--skip-files-check`, `--ack-revision`, `--allow-replace`, `--prod-url`, any `PROD_*` variable, any gate-side client flag that lifts a cap.
- Nonexistent for now (removals deferred, decision 27; the design text is kept in P2 and P3 under "Deferred phase: removals"): `--retire`, `--allow-mass-retire`, `--force-orphans`, `--retired`, `--max-retired-age`, `--max-pull-age`, `--date`, `--names-file`, the `retire` and `restore` subcommands of `sync.files`, any `prune` flag.

Exit codes (all tools): 0 clean (or dry run, **also when the report says a guard would trip**: the apply then refuses with 3); 1 other failure (a partly applied run lists what is committed); 2 handshake or precondition failed (including a held lock);
3 a guard tripped before any write (P6: only warnings with `--fail-on warn`); 4 verification found differences (P6: any check with status `error`; a left-behind finding is never one).

## k. The dry-run report (decision 26)

Every sync operation (`sync.run`, `sync.promote`, `sync.files promote`, `sync.pull`, and `sync.verify` as a report of drift) is a dry run unless `--apply` is given, and **every run, dry or applied, produces a report** of what would be
added and what would be overwritten. The report module is `sync/report.py` (SC); the designs only say which categories their tool fills.

**Files** (in `runs/<runid>/`, section a): `report.json` (machine-readable, complete; only the id lists of large pulled tables are cut at `sync.report.max_ids`, with a count and range instead) and `report.md` (human; the same sections; every list capped at the first N ids, `--top N`, default `sync.report.top_n` = 50, with a line "N more in report.json").
The same content is printed on stdout in summary form (headline counts and bytes per section, guards that would trip, plan hash, the apply command) and, if `--json PATH` is given, `report.json` is also written there. A dry run writes them into a folder
carrying the `dry` marker (no consumer accepts it as input; the report is for the owner). An apply writes the same files into its own folder with `dry: false` and an extra `result` block (what was actually committed, per section). A run that fails the handshake or a
precondition (exit 2) still writes a report holding the handshake and precondition results and nothing else.

**Categories** (per tool, and within it per table or per file set; a section is one tool's part of the report):

| Category | Meaning | Detail |
|---|---|---|
| `added` | new on prod (images, rows, files, global-set members, pulled rows new on dev) | count, bytes, complete id list |
| `overwritten` | exists on the target and differs | count, bytes, id list. **Images:** each id with the **digest groups that changed** (`core, ocr, clip, desc, tags, profile, note`) and a count per group. **Files:** `size_changed` / `hash_changed` counts and ids. **Pull:** rows replaced on dev, per table |
| `unchanged` | exists and equal | count (no id list in `report.md`; ids in `report.json` only for a section with fewer than 1000) |
| `skipped_with_reason` | would not be written, one entry per reason code: `count`, `ids` | reason codes: problem images (`missing_file`, `name_problem`, `hash_mismatch`, `missing_required_table`), `files_gate_miss`, `deferred_changed_since_plan`, `non_promotable_reference`, `waiting_for_files` (below) |
| `left_behind` | **informational (decision 27):** on prod but not promotable on dev (files not in the manifest, image rows flagged, cut, rejected or deleted on dev after promotion, global-set members dev no longer has, absorptions only prod has). Counts and ids (a file without an id: its name, as P6 F4 anomaly paths) | never an error, never a guard; header "left behind on prod (removals deferred)" |

Each section also carries: `totals` (added, overwritten, unchanged, skipped, left behind: counts and bytes), `guards` (`{id, tripped, value, limit, lifted_by}` for every guard of the tool, tripped or not), `estimate` (`{duration_s, wire_bytes}`), and its own `plan_hash`.
The document header carries: `env`, `run_id`, `tool`, `dry`, `generated_at`, the banner, `handshake[]` (`{step, ok, detail}` for H1 to H10 as run), `preconditions[]` (`{id, ok, detail}`), the `plan_hash`, the **exact `apply_command`** to run (for example
`python -m sync.run --env general --apply --plan-hash 3fa9...`), and `totals`. Pull sections list tables and bug reports (`to_fetch`, `to_delete_on_prod_after_verified_pull`) instead of images; a verify report lists the drift in the same categories (`added` = would be added by a promote, `overwritten` = differs,
`left_behind`) next to its check results (P6).

**Plan hash.** A canonical hash (sorted keys, sorted ids) over the plan: for each section the category sets (ids and, per overwritten image, its changed groups), the file manifest hash, the guard decisions, the flags that change the plan. It excludes `generated_at`, run ids, estimates and bytes
that are measurements. `--apply --plan-hash H` re-plans first and refuses with exit 3 if the hash differs (the world changed since the owner read the report); without `--plan-hash` the apply still prints the new report and asks for the confirmation.
`sync.run`'s combined hash is the hash of the ordered section hashes.
**Exception, owner decision A (2026-11-14): the `sync.pull` section hash is structural.** It covers only the tables in scope, the ratings mode, the flags (`skip_files`, `bug_reports` enabled or not, `text_cap`) and each guard's id, tripped state and lifting flag. It does NOT include prod row ids, row digests, counts, guard values or the bug-report lists: readers change prod every minute, so a content-bound hash could never be applied. Those stay in `report.json` / `report.md`. The other sections keep the content-bound hash. Implemented as `Section.structural` in `sync/report.py`.

**`sync.run` is one combined document** with one section per step (`pull`, `files`, `data`, `verify`; the handshake results in the header). **Dependency note (printed in the report):** later sections depend on earlier ones being applied, so in a dry run the `data` section cannot see files that are not yet on prod: images
whose file the `files` section would add or replace are shown under `waiting_for_files` (count and ids), counted in the data section's expected `added` / `overwritten` totals and part of the plan hash. At apply time the data step plans for real after the files step, and an image whose file did not arrive moves to `skipped_with_reason: files_gate_miss` in the `result` block. Likewise the `verify` section of a dry run
describes the state before the apply.

**Redaction.** Reports contain ids, digest group names, table and file-set names, reason codes, counts, bytes and durations. Never message text, search text, rating text, row values, credentials or connection data; filenames only for a file that has no id (a left-behind file on prod) and for name problems as a
reason code plus the image id (the filename stays in `files-promoted.json`, where it already was). A report test feeds sentinel text through every source and asserts it is absent from `report.json`, `report.md` and stdout.

## Resolved calls (made while reconciling; each appears in the affected design's revision notes)

1. Files report max age is 2 h. (Pull-state max age 1 h and `retired.json` 24 h standalone belong to the deferred retire, decision 27.)
2. (Deferred, decision 27.) `retired.json` is the only retire evidence; it carries `superseded` (P2 copies the renames from `committed.json`) so P3 needs no other file.
3. (Deferred, decision 27.) The ratings guard (P2 retire, H1): the per-batch check always runs. `ratings_mode: skip` and no prod rating on the batch ids: trivially satisfied; `skip` and prod has ratings on them:
   blocked ("switch to `mirror` and pull"); `mirror`: blocked when prod's rows for the id differ from dev's mirror or have `updated_at` after `snapshot_at`.
4. `image_extras` becomes `replace_per_image` (P2-T1): it is the per-image remarks row of the `core` group, P2 already deletes it with the other child rows of a changed image, and a removed or cleared
   remark must leave prod; upsert plus a `prune` clause would need a per-table delete query that the replace path already is. `images` stays the only image-scoped upsert.
5. `sync_writer` has no `TEMP` (P2 L4).
6. The gate does not get the docker socket (root-equivalent): `containment` and `disk` print files written by a root timer.
7. `list` returns every entry with its type so P6 F4 can find non-regular files without a second verb.
8. `--allow-shrink TABLE` and `--allow-mass-change N` have the same shape in every tool; P4's former boolean forms are replaced (`--allow-mass-retire N` has the same shape and is deferred with the retire).
9. (Decision 26.) Every tool is dry run by default and produces the report of section k; `plan.json` is folded into `report.json`; the report module `sync/report.py` is part of SC; a dry run exits 0 even when the report says a guard would trip.
10. (Decision 27.) No removals are built: no `--retire`, no retire/restore/purge verbs, no prune. A replace of the derived rows of a changed image is an overwrite and stays. Orphans on prod are reported as `left_behind`, never an error.
