# A7 Duplicates Count Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Album sync status card shows how many of the uploaded files the server already had (answered `duplicate`), cumulative per environment, and how many uploads predate the count.

**Architecture:** A new nullable column `uploadAnswer` on `tracked_files` (Room migration 1 -> 2) records the server's answer per uploaded file; `TrackerCounts` gains `duplicates` and `unclassified`; the engine writes accepted and duplicate positions with their own answer; the status card renders two optional lines from pure mappers.

**Tech Stack:** Kotlin, Room (schema export), Hilt, Compose, JUnit/mockk, Room androidTest.

**Spec:** `docs/superpowers/specs/2026-11-08-android-ingestion-sync/2026-11-23-a7-duplicates-count-design.md`

## Global Constraints

- X in "X of Y uploaded" keeps including the duplicates (owner's decision): `uploaded` is unchanged in `TrackerCounts` and in the headline.
- `uploadAnswer` values: NULL (not uploaded or unclassified legacy row), `"accepted"`, `"duplicate"`. Persisted by name; constants live in `TrackerSql` and a test pins them (like `TrackerSqlConstantsTest` does for the states).
- Room: `version = 2` with an explicit `Migration(1, 2)` (`ALTER TABLE tracked_files ADD COLUMN uploadAnswer TEXT`), registered in `TrackerModule` with `addMigrations`; no destructive fallback; the exported `app/schemas/.../2.json` is committed.
- An already UPLOADED row is never rewritten by a later answer (as today: "late answer must not change history").
- Texts: `"215 already on the server (duplicates)"` (only when duplicates > 0) and `"12551 uploaded before this count existed"` (only when unclassified > 0). Strings inline English.
- The run summary line, the engine's behaviour, the upload content and the backend do not change.

## Review Focus

- The migration keeps every existing row and its state (a v1 database opens in v2 with the same rows and NULL answers): the androidTest `MigrationTest` pins it; the JVM side is the SQL string plus the exported schema.
- A response mixing accepted, duplicate and rejected entries writes each group once with the right answer; an empty group writes nothing.
- A re-sent file already UPLOADED (lost response) stays as it was; its answer is not overwritten (so a first `accepted` is never turned into `duplicate`).
- An album change / reset wipes the answers with the rows (counts return to 0/0/0).
